# IGDB移行と検証

## データの扱い

- 検索結果は `source: "igdb"` とIGDB IDを返す。投稿は `igdb_game_id` で送信する。
- 旧クライアントの `rawg_game_id` 投稿も対応する。両方のIDを指定した投稿は拒否する。
- 既存の `bgms.id`、`bgm_sets.bgm_ids`、localStorageのBGM IDは変更しない。
- 既存行のIGDB IDは自動補完しない。名前一致や同じ数値だけでRAWGとIGDBを紐付けない。
- `games` の明示的なID対応だけを登録時に利用する。対応のない旧BGMの同名曲・ゲーム名一致は重複候補として拒否し、勝手に統合しない。
- 管理者がゲームを変更した場合は、そのBGMのゲーム情報だけを更新する。新しいゲームとの対応が確認できない旧RAWG IDは、誤った関連付けを避けるためその編集対象から外す。同じIGDBゲームの再選択では既存のRAWG対応を維持する。
- 管理者編集はSupabaseアクセストークンをサーバーで検証し、許可された管理者だけが実行できる。
- 検索はDBを更新しない。既存辞書を読み、IGDB結果はプロセス内で5分間キャッシュする。新たな別名の永続保存は行わない。

## 検索

`モンハン`、`モンスターハンター`、`monster hunter`、`monsterhunter`、全角英語を同じ検索語に変換する。ポケモンの日本語名・アクセント・Version表記にも対応し、ブラック2・ホワイト2などの併記は別々に検索する。その他の日本語入力はIGDBのalternative_namesとgame_localizationsも調べる。網羅的な翻訳辞書ではない。

既存ローカル別名に一致する語があり、IGDBの直接検索が0件なら、その正式名で最大3件の追加検索を行う。IGDB IDのない辞書行はIGDBゲームとして返さない。

候補は一致度、正規化名、IGDB IDの順で並べ、6件を返す。入力と一致しない候補は除外し、保存済み候補への加点はない。IGDBがUpdateと分類しparent_gameを持つ候補は本編にまとめる。同名の別作品やDLCは統合しない。画面は400〜500ms待って検索し、IME変換中は検索を待機する。入力変更・閉じる操作で古いリクエストを中止する。

## ゲーム別BGMとユーザー機能

- ゲーム選択→登録済みBGM一覧→見つからない場合のみ新規登録、の導線を追加。
- ゲーム別一覧と重複チェックはIGDB ID、明示的RAWG対応、正式名の完全一致の順に確認する。第三者の別名だけで旧BGMを別ゲームに分類しない。表示上の照合であり、旧行へのID書き込みはしない。
- 同じゲームの表記揺れ・1文字の誤字を確認するヒントと、登録前の確認欄を追加。意味の異なる曲や別ゲームの同名曲を自動統合しない。
- 不適切な特定フレーズをサーバーと登録画面で拒否する。辞書型の検査ですべての不適切表現を網羅するものではない。既存行は変更しない。
- 一覧の人気順は公開MY 9に含まれる回数。1セット内は1回として数え、同数はBGM ID順。
- カード下部のドラッグ操作でSELECTED BGMへ追加。既存の並べ替え、＋ボタン、9曲上限、重複防止、共有ページの読み取り専用を維持。
- 三点メニューに既存の通報、管理者編集・非表示・再表示を集約。
- 一般向けログイン・新規登録は使用せず、トップで入力した名前を公開時の作成者名として保存する。入力名はブラウザー内にも保持する。既存の管理者UID判定と管理API認証は変更しない。
- 公開セットの作成者名は公開時点の名前を保存する。過去の匿名セットの所有者は推測しない。メールアドレスは公開セットに保存しない。
- 公開完了画面から、共有URLと「私を彩る9つのBGM」「#My9BGM #私を彩る9つのBGM」を入力済みのX投稿画面を開ける。
- 共有セット閲覧時は編集用の名前・検索・追加一覧を隠し、作成者名、左側の3×3画像、右側の9曲一覧を表示する。

OAuthトークンは有効期限まで再利用し、401時は1回更新する。IGDB通信はプロセス内で直列化し275ms以上間隔を空ける。複数のVercelインスタンスにまたがる全体のレート制限ではない。IGDB障害時は利用可能なローカル候補を返し、それもない場合は502を返す。

## DB

手動適用SQL: `supabase/migrations/20260910_prepare_igdb.sql`

`bgms.igdb_game_id`、IGDB側の重複防止インデックス、IGDB専用ゲームのための `games.rawg_game_id` のNULL許可を用意する。既存データ、RLS、RPCの自動変更はしない。

追加SQL（未適用・所有者確認待ち）: `supabase/migrations/20260910_set_creators.sql`

`bgm_sets.creator_id`と`creator_name`をNULL許可で追加する。既存のBGM、公開ID、9曲の並び、RLSポリシーは変更しない。SQL未適用でも匿名公開・既存共有リンクは従来どおり動く。ログインしての作成者名付き公開は設定完了まで503で案内する。

## コマンド

```sh
npm test
npm run build
```

書き込みを伴う検証には実DBを使わず、次を別ターミナルで実行する。

```sh
npm run test:fixture
npm run test:localhost
```

`test:fixture` はOSの一時フォルダーにアプリをコピーし、localhost:3001で起動する。実際の `.env.local` はコピーせず、Supabaseは127.0.0.1:4011のメモリDB、IGDB/OAuth/画像はテスト応答に差し替える。サーバーからのその他の外向き通信は拒否する。ブラウザーで直接読み込む公開画像は元のCDNを使う。アプリ修正後はfixtureを再起動してコピーを更新する。

テスト管理者: `admin@example.test` / `fixture-password`（実アカウントではない）。
一般ユーザー: `member@example.test` / `fixture-password`。新規登録画面もメモリ内だけで検証できる。

- BGM追加から4表記とポケモン日本語併記、Honkaiを検索し、候補を選んで投稿する。
- 管理者でログインし、追加したBGMのゲームを変更する。
- `http://localhost:3001/?set=fixture-shared` で既存9曲の並びを確認し、PNGを生成する。
- `test:localhost` はテストDBを初期化してから、登録・重複・旧投稿契約・編集の認証・画像プロキシ・公開セット保護を検証する。
- 入力した作成者名の保存、一般ユーザーの管理者編集拒否、不適切語のAPI拒否も確認する。
- 終了時はfixtureのターミナルでCtrl+C。実DBには書き込まれない。

実IGDBの検索とCDN画像の確認は通常のlocalhost:3000でも行う。通常環境の投稿・編集は実DBへの書き込みになるため、テストデータの送信には使わない。

## 検証時点の制限

リポジトリ全体のlintには、今回の変更前からある内部リンクとReact Hooksのエラーが残っている。今回追加したライブラリ・API・テストのlintは個別に確認する。SQLの一意制約や実際のRLS動作そのものはメモリDBテストでは証明されない。
